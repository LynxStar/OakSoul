# OakSoul

OakSoul is a hobby project for driving game clients on a personal private MapleStory server using computer vision, without modifying the game client or the server. The long-term goal is AI-driven allies that play alongside the owner.

The approach: capture each client window with ScreenCaptureKit, run vision on the frames, decide, and later inject input. Input is out of scope for now. This first milestone is the capture layer, a per-window frame recorder.

## Prerequisites

- macOS 14 or newer
- Xcode Command Line Tools (provides `swiftc`; full Xcode is not required)
- .NET 10 SDK
- ffmpeg on PATH (for example `brew install ffmpeg`)

## Build

```
dotnet build OakSoul.slnx
```

The build compiles `native/OakSoulCapture/Capture.swift` with `swiftc` into `native/out/liboaksoulcapture.dylib` and copies it next to the built binaries.

## Run

List shareable windows:

```
dotnet run --project src/OakSoul.Recorder -- --list
```

Record one minute of a window chosen by process ID and exact title:

```
dotnet run --project src/OakSoul.Recorder -- --pid 1234 --title "Exact Title" --seconds 60
```

Record by window ID with the x264 4:4:4 preset, a keyframe every second, and the macOS title bar cropped off:

```
dotnet run --project src/OakSoul.Recorder -- --window-id 5678 --encoder x264 --keyframe-every 1 --crop-top 28
```

Window selection is exact. There is no fuzzy matching, and if zero or several windows match, the recorder refuses and says so.

## Options

```
--list                     print every shareable window and exit
--window-id N              capture this window ID (from --list)
--pid N --title "T"        capture the window with this exact title owned by this process
--app "Name" --title "T"   same, matching the owning application's name instead of pid
--fps N                    frames per second to request (default 30)
--seconds S                stop after S seconds (default 0 = until Ctrl-C)
--out DIR                  root for session folders (default recordings)
--name NAME                session folder name (default timestamp + window title)
--keyframe-every S         seconds between lossless PNG keyframes (default 2, 0 = none)
--encoder P                x264 (default, readers stay exact), x264-420, hevc, h264vt, lossless
--ffmpeg-args "..."        raw encoder arguments instead of a preset (use with --ext)
--scale N                  capture at N times the point size and keep the bottom-right pixel of every
                           NxN block, so frames are the game's own pixels at point size (default:
                           the backing scale of the window's display, 2 on Retina; 1 = capture at
                           point size, which ScreenCaptureKit blurs on a Retina display)
--width N --height N       raw capture size in pixels, no decimation; excludes --scale above 1
--queue N                  frames buffered between capture and encoder (default 30)
--crop X,Y,W,H             capture only this region of the window, in points from its top-left
--crop-top N               drop N points from the top, e.g. 28 for a standard macOS title bar
```

A windowed CrossOver client carries a standard 28 point macOS title bar, so `--crop-top 28` yields frames of exactly the game's native size (1366x768 for a 1366x796 window). The crop is applied by ScreenCaptureKit before scaling, and `session.json` records it.

On a Retina display the compositor shows the game's 1x render as 2x2 blocks. By default the recorder asks ScreenCaptureKit for the region at that backing scale (2732x1536 for the crop above) and keeps the bottom-right pixel of every block as each frame arrives, so frames are still 1366x768 but hold the game's own pixels; colours come in sRGB rather than the display's Display P3. `--scale 1` captures at point size instead, which ScreenCaptureKit produces by blurring the 2x image, so use it only on a non-Retina display. The recordings made before this (`fx-combat`, `fx-maps`, since retired) were blurred and colour-shifted; [docs/capture-notes.md](docs/capture-notes.md) has the measurements.

Exact capture of a windowed client, and the old point-size capture:

```
dotnet run --project src/OakSoul.Recorder -- --pid 1234 --title "MapleStory" --crop-top 28
dotnet run --project src/OakSoul.Recorder -- --pid 1234 --title "MapleStory" --crop-top 28 --scale 1
```

## Encoder presets

| Preset | ffmpeg arguments | Container |
|---|---|---|
| `x264` (default) | `-c:v libx264 -preset veryfast -crf 18 -pix_fmt yuv444p` | mp4 |
| `hevc` | `-vf pad=... -c:v hevc_videotoolbox -q:v 65 -pix_fmt yuv420p -tag:v hvc1` | mp4 |
| `h264vt` | `-vf pad=... -c:v h264_videotoolbox -q:v 65 -pix_fmt yuv420p` | mp4 |
| `x264-420` | `-c:v libx264 -preset veryfast -crf 18 -pix_fmt yuv420p` | mp4 |
| `lossless` | `-c:v libx264rgb -preset veryfast -qp 0` | mkv |

With `--ffmpeg-args` the container defaults to mkv unless `--ext` is given. Only `lossless` (or raw arguments using libx264rgb at `-qp 0`, FFV1, PNG or raw video) keeps the captured pixels in the video, which the entity detector needs to run on a replayed video (see Replaying recordings); it takes about 0.3 to 0.5 GB per minute of play (fx-combat-exact 1.47 GB for 192 s, fx-maps-exact 1.93 GB for 357 s). The default is `x264` because recordings double as test fixtures: re-encoding the lossless keyframes with each preset and running the readers on the decoded frames, `x264` at CRF 18 read all eleven frames exactly (glyph distance 2) while the hardware `hevc` preset at q65 read HP on five, MP on six and EXP on none, so use `hevc` only for long archival recordings where exact reads do not matter. Sizes are in [docs/capture-notes.md](docs/capture-notes.md).

## Session folder

Each run creates `recordings/<timestamp>-<title>/` (or the name given with `--name`):

| Path | Contents |
|---|---|
| `video.mp4` or `video.mkv` | Constant frame rate video from ffmpeg; `videoFrame` in `frames.jsonl` is -1 for frames left out of it |
| `keyframes/NNNNNNN.png` | Lossless PNG every N seconds; the number is the frame sequence |
| `frames.jsonl` | One JSON line per frame: `sequence`, `pts`, `wallClockUtc`, `videoFrame`, `keyframe` (path, only on keyframes) |
| `session.json` | Summary: window (with its display's scale), frame size, capture size requested from ScreenCaptureKit, scale, colour space, encoder arguments and `lossless` (whether the video holds the captured pixels exactly), duration, delivered, dropped, idle, filled, skipped and cut counts, mean frame copy time, keyframe count, video bytes, ffmpeg exit code |
| `ffmpeg.log` | ffmpeg output |

ScreenCaptureKit only delivers a frame when the window changed, so the video fills gaps of up to two seconds by repeating the previous frame (`filledVideoFrames`). Longer idle stretches are cut out of the video (`cutSeconds`), and a frame that arrives ahead of the constant-rate timeline is left out (`skippedVideoFrames`). The metadata keeps the true timestamp of every frame either way.

The recorder stops cleanly on Ctrl-C, SIGINT or SIGTERM: the capture stops first, the remaining frames are written, ffmpeg finalizes the file and `session.json` is written. ffmpeg runs in its own process group, so the terminal's Ctrl-C reaches only the recorder; SIGINT and SIGTERM are handled explicitly as well, since a recorder started as a background job of a non-interactive shell ignores SIGINT, and SIGTERM would otherwise end it without the clean stop (fx-maps-exact's `session.json` had to be reconstructed after such a stop).

## Permission

Screen Recording permission is granted per responsible application. When running from Terminal, allow Terminal under System Settings > Privacy & Security > Screen Recording. Without it, listing windows times out or returns nothing.

## Vision

`src/OakSoul.Vision` holds the HUD attention regions for the client at its native 1366x768 (title bar cropped) in `Layouts/hud-1366x768.json`, loaded through `HudLayout.Native1366x768`. Each region has a name, a kind (fixed, provisional, or dynamic), a rectangle in frame pixels from the top-left, and a note on what gets read from it. Edit the JSON to move a region; the loader rejects rectangles that do not fit the frame. `world.viewport`, where the entity detector looks for the world, is the whole frame; the bottom HUD with its shadow (`hud.bottom`) and the window's rounded bottom corners are masked out of it as measured, and the other HUD regions as before (see The bottom corners).

`FrameGeometry` maps that native layout onto any captured frame. The client aspect-fits its render into the window, so a frame is the native image at one uniform scale, centered, with black bars on the spare axis; `FrameGeometry.Detect` computes the scale and offset from the frame size, checks that the predicted bars are black (an uncropped title bar fails this check), maps rectangles and points both ways, and `ExtractNative` resamples a region back to its native size so readers are written once for native pixels. Verified on a fullscreen 1728x1116 recording: content 1728x972 at offset 72, scale 1.265.

### Readers

`StatusReader.Read(geometry, frame)` returns HP, MP and EXP from one frame: the exact numbers from the text row, and each bar's fill ratio as an independent cross-check.

- **Numbers** come from matching binarized glyphs against the client's own bitmap font, embedded as `Fonts/status-font.json` and learned from frames whose values were known (`GlyphFont.Learn`). Label letters are skipped because they fill the top of the text band where digits leave two empty rows; the green brackets split the EXP total from its percentage; touching digits are split at their thinnest column. On native frames every glyph matches at distance zero.
- **Bars** are measured from their highlight line and the run of saturated columns, so they survive small layout shifts. They read about one percent high on HP; the numbers are the authoritative value.
- **Scaled frames** are best effort: the reader tries three ink thresholds and keeps the reading with the fewest unknown glyphs. On the 1.265x fullscreen recording HP read exactly on every keyframe, MP on three of five and EXP on four of five; the misses are blurred glyphs reported as `?`, never wrong digits.

`MinimapReader.Read(geometry, frame)` returns the minimap panel as drawn, the map image inside it, the player's own dot and every other marker. The panel's top-left corner is fixed but its size follows the map, so the right edge is anchored on the orange WORLD button in the title bar and the bottom on the border colours down the left side; the map image sits at fixed insets inside. Dots are colour blobs: yellow is you, red other players, teal portals. `SelfInMap` gives your dot relative to the map image, which is what the server's minimap metadata will turn into world coordinates. About half a millisecond on a native frame. Collapsed, the panel is a 20-row bar reading "Region : Map" followed by the minus, plus and WORLD buttons; there the WORLD caption crosses the title-bar row, so the button is found on the rows above and below its caption instead, which gives the bar's true width (215 on fx-anttunnel, 284 on the retired fx-maps' Perion Street Corner, where the reading used to stop at the minus button, 149 and 219) and `NameRight`, the column where the buttons start, 62 columns before the WORLD button's outline. The panel with its name block hidden but its map shown (the retired fx-maps around 1:02) also reads as collapsed, since the name block is what the check looks for; its left border runs on past the bar, so it gets no `NameRight`.

`MapNameTracker` reads the region and map names (for example Dungeon and Ant Tunnel IV) through Apple's Vision text recognizer, exposed by the shim as `TextRecognizer`. It only re-reads when a coarse hash of the name block changes, so the roughly 30 ms OCR cost is paid on map change rather than per frame; the first call takes a few hundred milliseconds while Vision loads. Validated on all sixteen keyframes, windowed and fullscreen alike. On the collapsed bar the text is read up to `NameRight`, so neither the button captions nor the world beyond the bar (whose scrolling kept the hash from settling: fx-anttunnel's bar was read on its eighth keyframe) enter the crop; where the buttons were not found it falls back to a generous span and cuts the text at the WORLD caption, which OCR does not always read whole (`WORL`, `WORLO`, `WORLE` and `WORLI` on fx-anttunnel; any word after the first that is a prefix of WORLD or one letter off it, also glued to the numeral as in `IVWORL`). With `IsKnownName` set (the watcher checks the catalog), a pixel-exact frame whose softened name block reads as a name the catalog does not know is read once more unsoftened, and that reading is kept when the catalog knows it (see Exact frames). After each read `NameWidensPanel` says whether the name text reaches within 24 pixels of the panel's right edge, so that the panel may be as wide as it is for its name rather than its map (5 or 6 pixels on the retired fx-maps' five such panels, 8 to 11 on Rocky Road, 53 or more elsewhere); the world tracker uses it to tell apart the maps a misread name may be.

**Exact frames.** The OCR readers were tuned on point-size captures, which ScreenCaptureKit blurs. On exact captures (`fx-exact`, and the keyframes of the diagnostic 2x recording `fx-2x`, since retired, decimated) Vision misread the game's sharp pixel fonts: the status bar's LynxHope as LunxHope at every upscale from 4x to 10x, the map name as Deep Valley !, and on fx-2x the level badge as 3. So `OcrInput` softens every OCR crop of a pixel-exact frame with that same capture kernel before Vision sees it, which reads LynxHope and Deep Valley I on all 40 of those keyframes, and leaves blurred frames as they are. A frame counts as exact when the status bar's job and name text shows one-pixel strokes at full contrast (177 luma levels above the background on exact frames, at most 129 after the blur on every keyframe of the retired fx-combat and fx-maps), so live captures and recordings of either kind need no flag. The level badge is also redrawn as black ink on white paper before OCR: its white digits on orange tiles read only at 8x before, and now read 31 at 6x, 8x and 10x on every keyframe of all four recordings (bar fx-maps' black transition frames). On an exact frame the badge is binarized as captured, not softened first: softened, LV. 32 read as "3 2" at 8x on every keyframe of fx-anttunnel and fx-anttunnel-open, which the parser then rejected, so the level stayed unknown; unsoftened it reads 32 at 6x, 8x and 10x there and 31 still at all three on fx-exact and fx-2x. The parser also joins the digits of all number lines right of the label, left to right, so "3 2" or separate "3" and "2" lines read as 32. Softening is still right for the map name block in general (Deep Valley I), but not always: Ant Tunnel IV's block on fx-anttunnel-open reads "Ant TunnelM" softened at the 3x upscale used, on every keyframe, and "Ant Tunnel IV" unsoftened, which is why an unknown softened name is read again unsoftened. Map names accept `!` as the numeral I (fx-maps itself had read East Rocky Mountain I as East Rocky Mountain !). The minimap reader finds the panel's right and bottom edges on both kinds of frame: on an exact frame the WORLD button's dark outline directly follows its orange run, and the bar's lowest light-blue row sits right on a dark line and passed for the white bottom line; before that fix the panel read as missing or up to 440 wide, so the names were never read. On all 20 fx-exact keyframes the panel now reads 191x220 as on fx-combat, and from the second keyframe on (the first is the stability gate) the level reads 31, the name LynxHope and the map Warning Street / Deep Valley I with its id 10004100. HP, MP and EXP already matched their glyphs at distance 0 on exact frames, since the glyphs are binarized. The readings of fx-combat and fx-maps are unchanged apart from that one map name.

### Character, quickslot and buffs

`NameTagLocator` finds your own character by its name tag, in the rows above the chat bar (the layout's `own_tag.search`, 1366x702: the world viewport takes the whole frame, and the status bar below shows the name too). The client renders a tag as light text on a translucent dark box, identically every frame, so the locator learns a binarized template once, from a frame where Vision OCR sees your name on its own (the name is the one given to the watcher with `--name`, the status bar only being checked against it), and then matches by pixel signature: nearly all text pixels bright, nearly all gap pixels dark, judged as a combined fraction so a bright background behind the box still matches. It searches near the last hit first and falls back to that whole area; about 20 ms per frame on misses, far less while tracking. On the point-size combat fixture (fx-combat, since retired) it placed the tag on three quarters of the keyframes, and the misses are frames where another tag or a mob overlaps yours. `NameTagHit.Feet` is the point just above the tag, which is where the character stands. The OCR line may differ from the status bar's name by one substituted character (Vision reads y as u and p as n on this font; a line with a character more or less is not taken, since the template is cut from its box), and edge columns that cross the box's dark margin rows above and below the text are cut from the template, so world art beside the box does not join it. On an exact frame an unhidden tag matches the template pixel for pixel, so when the strict match fails there, the tag is looked for within 128 pixels of where it was last seen by the share of its text columns that match exactly: a tag under a lightning bolt, a rope with the pet's tag, or the pet itself kept 53 to 88% of them on fx-exact, nothing else in the viewport (the tag one pixel off included) more than 33%, and 45% is required. That search runs before the whole-area one and finds a hidden tag in 15 to 30 ms; when the tag is gone it adds about 15 ms to the miss. Blurred frames keep the strict match alone, since soft edges cost an unhidden tag up to 30% of its columns there. On fx-exact the feet are known on 17 of 20 keyframes; of the other three, the first comes before the name is read, on the second OCR read the tag as LynxHopell (learned one keyframe later), and on the third the tag is under the chat bar.

The name can appear elsewhere on screen: the party window lists LynxHope as dark text on a grey panel, and on fx-anttunnel it was the only line reading the name on the keyframe where the name became known, so the template was learned there (16x19 of lit cave art, feet at the top right). So `TryLearn` cuts a template from every line reading the name and keeps only those shaped like a tag: a text band 6 to 12 rows high (11 for LynxHope, ascender to descender; 10 or 11 on the blurred fixtures), light text at least three quarters of the OCR line's width, the box's dark margin in the two rows above and the two below the band across at least 90% of its columns, and at least half the band dark. The party window's lines failed on band height (13 to 21 rows) and margin (at most 0.87) on all eleven keyframes where OCR read the name there on fx-anttunnel and fx-anttunnel-open, while the 155 tags accepted on all five fixtures (one per keyframe at most) had bands of 9 to 12 rows, margins of 0.93 or more and bands at least 0.64 dark. Of several qualifying lines, exact readings first, the one nearest where the camera keeps a resting character (tag top centre at 683, 491) wins. Edge columns lit only outside the text band are trimmed too (the pet's tag next to the own one made fx-anttunnel-open's template 58 wide; now 54). A template that never matches on any frame after the one it was cut from is forgotten after six misses and its place is not learned from again (the watcher prints `tag forgot ...`); one that matches once is kept for good.

`QuickslotReader` reads the eight cells: which key, whether the cell holds anything (an empty cell is flat grey in the middle), a fingerprint of the icon, and a fingerprint of the count corner. The item counts themselves are tiny anti-aliased digits drawn over the icon art at the same brightness as the art, and no thresholding separates them, so they are not read as numbers; instead `CountChanges` reports the cells whose count corner changed since the last frame. On the retired fx-combat those events lined up exactly with the potions used. A bot that knows a starting count can count down from the events.

`BuffReader` reads the buff row at the top-right. A slot is occupied when it correlates with a buff icon the reader has been taught (`Learn`, `Save`, `Load`; the watcher loads `recordings/known-buffs.json` if present), compared outside the corner that shows the remaining minutes. Correlation rather than difference, because the client draws the icon faded on roughly a third of frames, reported as `Faded`. The minute digit is not read yet, and the slot pitch has only been seen with one buff active.

### Live watcher

`OakSoul.Watch` runs the readers on a live capture and prints a line whenever a value changes:

```
dotnet run --project src/OakSoul.Watch -- --pid 1234 --title "MapleStory" --crop-top 28
```

It takes the same window selection as the recorder plus `--name`, `--crop-top`, `--fps`, `--seconds` and `--scale`. Like the recorder it captures exactly: the region is requested at the backing scale of the window's display (2 on Retina) and each frame decimated to the game's own pixels in sRGB, so the readers see what the game drew; `--scale N` overrides the factor, and `--scale 1` captures at point size, which ScreenCaptureKit blurs on a Retina display (the readers handle both, see Readers; the entity detector skips such frames, see Entities). Each line shows level, job and name, HP with its percentage, MP, EXP total and percent, region and map name, your minimap position and the number of other players on the minimap, your feet position from the name tag, the occupied quickslot keys and the active buffs (a `~` marks a faded icon), with a `*` after each field that changed. Quickslot count changes print as their own lines. Every ten seconds a heartbeat reports frames, frame rate, reader time per frame and dropped frames; the readers cost well under a millisecond per native frame. If the frame does not match the native layout, for example a windowed client captured with its title bar, it says so and suggests `--crop-top 28`.

**The character's name.** The watcher does not discover who is playing; the operator provides the name with `--name NAME` (default `LynxHope`, the only character so far) and it prints `name     LynxHope` among its startup lines. The name tag locator is created from the first frame with that name, instead of waiting for the status bar to be read, and the same name is the own name for entity tracking. The status bar is only checked against it: the name line is reported as the configured name when OCR reads it ignoring case or one substituted character off (Vision's slips on this font), and as read otherwise, so a different character logged in shows in the lines; the first time it differs the watcher prints `warning: status bar reads 'X', expected 'LynxHope'` once. Replayed on the five fixtures of the time the readings were the same as when the name came from the status bar, except that the tag is learned on the first keyframe of fx-exact, fx-anttunnel and fx-anttunnel-open (it was the third), so their first two keyframes now show a feet position and, where the world model runs, a camera placed with it; fx-combat and fx-maps (since retired) learned it on the same keyframe as before and read identically. With `--name Nobody` on fx-exact no tag is learned and the warning prints once.

**The pet.** A character has at most one pet, and its name is given the same way: `--pet NAME` (default `Mara`; `--pet none` for a character without one). The watcher prints `pet      Mara` next to the name, the overlay stream's header carries it as `pet`, and `OakSoul.Bake regenerate` passes `--character NAME` and `--pet NAME` on as the watcher's `--name` and `--pet`. Both are per-character settings; options are enough while there is one client (a character profile can come later). The name is never learned: from the first frame a tag reading the pet's name alone (a letter off allowed, `lara`) is the pet's, and OCR only checks it: when a plain name other than the own one is read beside the character three times before the pet's name ever was, the watcher prints `warning: the tag beside the character reads 'X', expected the pet 'Mara'` once.

### Replaying recordings

The watcher takes a recorder session folder instead of a window, so the whole pipeline after capture runs on real game samples with the game closed:

```
dotnet run --project src/OakSoul.Watch -- --recording recordings/<session> --keyframes --crop-top 28 --speed 0
```

`--keyframes` replays the sparse PNG keyframes, which are lossless copies of the captured frames; without it the video is replayed frame by frame. A video recorded with the `lossless` preset holds the captured pixels too (fx-combat-exact's and fx-maps-exact's decode to their keyframes byte for byte), and `RecordingFrameSource` says so from `session.json` (`lossless`, or for older sessions the encoder arguments); the source line reads `lossless video of ...` and the entity detector runs on every frame. A lossy video (`x264` and the other presets) moves sprite pixels by several levels (docs/capture-notes.md), so the readers run on it but the entity detector skips its frames, prints `entities skip frames: lossy video ...` once and counts them. `--speed 1` paces playback at the recorded rate, `0` runs as fast as frames decode. `--crop-top` applies to replay exactly as it would have at capture time, for sessions recorded with the title bar. Under the hood every consumer takes an `IFrameSource`, with `CaptureFrameSource` for live windows and `RecordingFrameSource` for sessions.

**Frame numbers.** A replayed frame keeps the capture sequence and pts it was recorded under (`Frame.Sequence`, `Frame.Pts`), so everything downstream names frames the way the recording does: a keyframe by its file name (`0001411.png` is sequence 1411) with the pts of that record in `frames.jsonl`, a video frame by the record whose `videoFrame` it is. A video frame the recorder wrote to fill an idle gap (`filledVideoFrames`; ScreenCaptureKit delivers nothing while the window is unchanged) has no record of its own: it comes with `Frame.Filled` set, the sequence of the captured frame it repeats and that frame's pts plus its offset on the video timeline, so sequence and pts together stay unique. A keyframe without a record (fx-maps-exact's last, written after the last metadata flush of its interrupted recording) gets a pts extrapolated from the record before it, and the watcher says so. `Frame.Index` counts frames by position in the replay and `Frame.Clock` is the playback clock, (Index - 1) / fps with keyframes counted one per second, which the world and entity trackers have always been timed with, so readings do not change: replayed on all five fixtures, keyframes and video, every printed reading of the watcher, the world report and the entity report matched the previous build line for line once timings and numbering are set aside. What did change is numbering: the `t=` stamps are now the time into the session (fx-combat-exact's keyframes, written every half second, used to be stamped a second apart), and the world report, the entity report and the contact sheets name frames by capture sequence. The detector still counts frames by position in the replay, which stays unique where fills repeat a sequence, and so do `OAKSOUL_DEBUG_FRAMES` and `OAKSOUL_SPRITE_DUMP_FRAMES`; frame numbers quoted in this README before the overlay stream existed (keyframe 49, frame 342 and the like) are such positions too (keyframe 49 of fx-combat-exact is sequence 721).

### Fixture recordings

Recordings under `recordings/` (gitignored) are the test fixtures. All of them are exact captures (`scale` 2 and `colorSpace` sRGB in their `session.json`), and the two long ones have a lossless video besides the keyframes:

- `fx-combat-exact`: 192 seconds of combat on Warning Street / Deep Valley I (10004100) at level 32, 5,622 frames with 377 keyframes every half second and a lossless video (`-c:v libx264rgb -preset veryfast -qp 0`, 1.47 GB, which decodes to the keyframes byte for byte). The main detector fixture: Red Snails, Dark Axe Stumps, Dark Stumps, Wild Boars, Fire Boars, a Blue Snail and two Axe Stumps, the pet Mara, another player, meso and item drops, steam and frozen mobs, 61 EXP gains.
- `fx-maps-exact`: a 357-second walk from Ellinia to Deep Valley I, through Ellinia Department Store, The Field Up North of Ellinia, The Tree That Grew I, The Forest North of Ellinia, East Domain of Perion, Rocky Road III, II and I, East Rocky Mountain I, Perion Street Corner and Perion, with 347 keyframes (about one a second) and a lossless video (1.93 GB). Its `session.json` was reconstructed after the recorder had been stopped with SIGTERM before it handled that signal, and says so in a `reconstructed` field (counts past the last metadata flush are unknown). Replayed through the watcher it yields the complete, correctly spelled timeline of those fourteen maps.
- `fx-exact`: ten seconds on Deep Valley I (20 keyframes, x264 video), the first exact fixture for the readers.
- `fx-anttunnel` (5 s, 10 keyframes every half second) and `fx-anttunnel-open` (5 s, 11 keyframes): Dungeon / Ant Tunnel IV (10005063) at level 32, with a party window open at the top right listing LynxHope, and the minimap collapsed in the first (chat expanded over the character on keyframes 4 to 7) and expanded in the second, x264 video. They found the level badge read as "3 2", the party window taken for the name tag, the WORLD caption read as "WORL", and Ant Tunnel IV's name read as "Ant TunnelM" and resolved to Ant Tunnel I.

The point-size recordings `fx-combat` (403 keyframes of combat on Deep Valley I) and `fx-maps` (a 197-second walk from Perion to Ellinia), blurred and in Display P3, and the diagnostic 2x recording `fx-2x` have been retired: they and their contact sheets were deleted once exact capture replaced them. Measurements quoted from them in this README and in [docs/capture-notes.md](docs/capture-notes.md) were taken on them and stand. Each fixture has found something: the hazy Perion sky defeating the old panel-bottom scan, the collapsed minimap, roman numerals read as "IIl", and the bold W in "Wizard" (fx-maps); more Axe Stumps than the client's spawn list and the pet's tag on mobs (fx-combat-exact).

## Map metadata from the client

`src/OakSoul.Wz` is a read-only reader for the client's WZ archives (the PKG1 format: header, version hash, encrypted offsets, property trees), and `src/OakSoul.MapExport` uses it to export every map's metadata to JSON:

```
dotnet run --project src/OakSoul.MapExport -- --list
```

## World model

`src/OakSoul.World` turns the readers' output into world coordinates using the exported map metadata. `MapCatalog` loads `data/maps` by id or by the street and map names the HUD shows; `FootholdIndex` answers which foothold lies under a point, which one the character stands on, which ladder or rope it is on, where the foothold chain leads, and the nearest portal; `MinimapTransform` converts the own dot to world and back; `CameraModel` holds the clamping and anchor rules; `WorldTracker` combines dot, name tag and metadata per frame into the map id, world position, camera, foothold or rope, and a confidence.

What the fixtures settled, with the measurements in the code comments:

- **Minimap.** The HUD draws the minimap canvas at a fixed quarter size, 16 world units per pixel (4 x mag), not stretched or fitted to the panel. The visible image is the reader's `MapArea` moved one column left and two rows down, 2 wider and 5 shorter. A map narrower than the panel (which widens for a long name) is centred; a map taller than the panel allows (Perion, Ellinia, East Domain of Perion, The Forest North of Ellinia: 112 rows shown) is a window centred on the player and clamped to the image, so on those maps the dot gives no height while the window is mid-map; the tracker then places the window from the portal markers, follows the foothold chain, or holds the camera. The own dot is drawn at the floor of its 16-unit cell, 6 pixels up, so the dot alone is good to +-8 units.
- **Camera.** It clamps to vr with the full 1366x768 frame as the view (not the 702 rows above the chat bar). The tag's `Feet` point sits 4 pixels below the soles. Unclamped, the camera eases towards the player with a dead zone: resting feet sit around x 683 (655 to 733) and y 490, and while walking the feet run about 122 pixels ahead of centre.
- **Portal activation area.** The client's data does not hold the area in which a character can enter a portal. `Map.wz`'s `MapHelper.img/portal` has only the portal art (the visible portal's frames are 84 to 88 pixels wide, 182 to 256 high, origin at the bottom centre) and the editor's icons; the maps' portal nodes have `pn` (name), `pt` (type), `x`, `y`, `tm` and `tn` (target map and portal) and, on 264 of the 3165, `script`, plus `delay`, `hideTooltip`, `onlyOnce`, `shownAtMinimap`, `horizontalImpact`, `verticalImpact` and `image` on a few, none of them a size. The rectangle is the Journey client's, a reimplementation of the game's client (`ryantpayton/MapleStory-Client`, `Gameplay/MapleMap/Portal.cpp` and `MapPortals.cpp`): `Portal::bounds()` is the portal's point plus (-25, -100) to (+25, +25), and `find_warp_at` enters the portal whose bounds contain the player's position, the soles. `Portal.Activation` is that rectangle (a spawn point has none), `Portal.Activates(x, y)` tests a point, and the overlay's portal items carry the rectangle as `rect`. fx-maps-exact (a walk from Ellinia to Perion and Deep Valley I) bounds it but does not fix its edges. Of its thirteen map changes twelve have a position (the one out of the department store has none: the names lagged and the own tag was not found). The screen starts to dim on the frame the client begins a change; taking the camera as clamped to the view range's left or right edge where the character stands far from the screen's centre (all but the first), the character's x is that edge plus the name tag's feet, exact to a pixel, where the tracker's own x is the minimap's 16-unit cell. Soles x relative to the portal's point, on the last frame before the dimming and 4 and 5 frames earlier: Ellinia to the department store +5 (unclamped, +-16, so not used below), to The Field Up North of Ellinia -8, -2, +2; to The Tree That Grew I -36, -22, -17; to The Forest North of Ellinia -11, -10, -9; to East Domain of Perion -9, 0, +5; to Rocky Road III +20 (the last read, 4 frames before, still walking right; the minimap dot says +23 at the end), +20, +18; to Rocky Road II -14, -10, -8; to Rocky Road I -23, -13, -8; to East Rocky Mountain I -24, -9, -4; to Perion Street Corner -22, -9, -4; to Perion -32, -19, -14; Perion to Deep Valley I -1, -2, -3. The heights, the foothold under the soles against the portal's y, are -5 to +4. So nine of the eleven are inside the 25 either side on the last frame and two (-36 and -32) outside by 11 and 7, but those two walked left at full speed, 5 pixels a frame, and like three others (-22, -23, -24) stopped dead one or two frames before the dimming, which is what the client freezing the character as the change begins looks like: the soles are where the walk ended, the press that started the change came earlier. With the press 4 frames before (133 ms) the positions are -22 to +20, with 5 frames -17 to +18, all inside. So the recording is consistent with the rectangle, and tells only that a character entered portals from about -17 to +18 pixels of the point (taking 5 frames), and nothing of the top and bottom edges, since every change was a walk on the ground. One hint that the edge may be nearer than 25: on the East Domain the character stood 17 frames (0.55 s) at -11 before it walked right and the change began at +20; nothing says Up was pressed during that stand.
- **Map changes.** The names lag the new panel by the OCR stability gate, so the tracker treats a change in the panel size as "map unknown" until the names change.
- **Misread names.** A reading that matches no map exactly is never resolved to its closest name alone: Ant Tunnel IV read as "Ant TunnelM" is closest to Ant Tunnel I. `MapCatalog.FindCandidates` returns every map within two edits (street and map together) and every map whose name before its last word starts the reading (all "Ant Tunnel *"), and the tracker takes the one candidate whose predicted image explains the minimap (`MinimapTransform.StrictSizeMismatch` within 1.5 pixels and better than every other): an image wider than the area never fits, a narrower one only when the name may have widened the panel (`NameWidensPanel`), a taller one only through the 112-row window. Ant Tunnel IV's 219x172 image explains fx-anttunnel-open's 219x112 area exactly, while Ant Tunnel I, II and III are 17, 39 and 6 pixels off; the retired fx-maps' "Rocky RoadI" and "The Tree That GrewI" still resolved, and East Rocky Mountain I and IV, which share a size, are left unknown. With the minimap collapsed or no candidate fitting the map stays unknown and is tried again on later frames.

`OakSoul.Watch` loads `data/maps` (or `--maps DIR`) and adds the map id, world position, foothold or rope, and camera to each line; `--world-report` prints the validation at the end of a replay (minimap model per map scored against portal markers, foothold agreement, camera anchor and bounds, self-consistency, and the portals used at each map change):

```
dotnet run --project src/OakSoul.Watch -- --recording recordings/fx-maps-exact --keyframes --speed 0 --world-report
```

## Entities: mobs, players, pets, drops

`src/OakSoul.Detect` finds what is drawn over a map and tracks it. Foreground is measured against a background learned from recordings, then verified and identified against the client's own mob frames (`data/mobinfo`, from `OakSoul.MobExport --sprites`), drop icons (`data/sprites`, from `OakSoul.SpriteExport --items`), damage number digits (`data/sprites/effect`, from `OakSoul.SpriteExport --effects`), and since review 2 the pets' frames, the mouse cursor, the meso coins' spinning frames with their origins and the character's own skill effects (`OakSoul.SpriteExport --pets --cursor --mesos --skill-effects 200,220`; each set is PNGs plus a `frames.json` with every frame's origin, delay and body rectangle, read from the property archive or pack its canvases are outlinks of). The project depends on Vision and World (which stay independent of each other).

The detector compares sprites with the screen pixel for pixel, so it runs only on frames that are the game's own pixels: an exact capture, live, from a recording's keyframes or from its lossless video. Any other frame is skipped, and the watcher prints the reason the first time and the count at the end (`entities: skipped 303 frames that are not the game's own pixels: 303 lossy video (replay its keyframes, or record with --encoder lossless)` for fx-exact's x264 video): a fullscreen or resized client (the client resamples its render; the geometry is not native), a point-size capture (no one-pixel strokes in the status bar, `OcrInput.IsPixelExact`), or a lossy video (`RecordingFrameSource.Lossless`, from `session.json`).

Build the background of every map a session visited (offline, from a pixel-exact session only, cached in `data/backgrounds/`, gitignored), then run the detector on the replay:

```
dotnet run -c Release --project src/OakSoul.Watch -- --recording recordings/fx-combat-exact --speed 0 --build-background
dotnet run -c Release --project src/OakSoul.Watch -- --recording recordings/fx-combat-exact --keyframes --speed 0 --entity-report --entity-sheet data/entity-sheets/fx-combat-exact
```

`--entities` prints a line whenever the counts by kind or the nearest mob change (`entities mob 5 player 0 pet 1 drop 0 effect 3 unknown 2  nearest mob #20 'Lv. 23 Dark Axe Stump' at 96 units`), `--entity-report` (implies `--entities`) prints the validation below, `--entity-sheet DIR` writes two contact sheets of twelve evenly spaced annotated frames (keep DIR under `data/` or `recordings/`), and `--backgrounds DIR`, `--mobinfo DIR` and `--sprites DIR` move the caches. Sheet labels name the mob, animation, frame and facing (`#116 Dark Axe Stump move/1R`; `~` when the identity is carried by the track rather than matched in that frame, `Mob?` for a mob nothing verified). For a closer look, `OAKSOUL_DEBUG_DUMP=dir OAKSOUL_DEBUG_FRAMES=16,200` writes full-size overlays of those frames with the foreground classes tinted (frames by their 1-based position in the replay, not the capture sequence: fx-combat-exact's capture 511 is video position 522), and beside each a blob view (`NNNN-blobs.png`): every pixel in one solid colour per kind (masked HUD black, your character magenta, background not trusted and not compared navy, clouds and steam green, tag boxes cyan, what an earlier step explained khaki, foreground too small or faint for a blob white, the matched background grey; legend at the bottom) and each blob in a colour of its own, boxed, with its number and the entity it became, and `OAKSOUL_SPRITE_DUMP=dir` (with `--entity-report`) writes, for every tagged or sprite-matched candidate, its surroundings beside the best frame and their difference at 3x (green where equal, yellow where the pixel fits through steam, red where not; `OAKSOUL_SPRITE_DUMP_UNMATCHED=1` adds the large unmatched ones on footholds, `OAKSOUL_SPRITE_DUMP_FRAMES=47,342` every candidate of those frames); `OAKSOUL_SPRITE_CSV=file` (with `--entity-report`) writes every scored candidate's best placement per species, and `OAKSOUL_TAG_DUMP=dir` every tag crop sent to OCR, as captured.

- **Background mosaic** (`MosaicBuilder`, `BackgroundMosaic`). Frames with a measured camera (dot and own tag) are stitched in world space over the map's vr box with the HUD regions (the bottom HUD and its shadow as measured, the buffs, the quickslot and the log), the window's rounded bottom corners, the minimap panel and a box around the own character masked out; beside the bottom HUD the corners are world down to the last row (see The bottom corners). Each frame is first registered to the pixel against the mosaic so far (the dot gives x only to +-8), then casts a streaming majority vote per pixel; a second pass counts how many camera positions agreed with the voted value (the background under steam or a name-tag box agrees too). The whole thing runs twice, the second round registering against the first round's reliable pixels. The mosaic is anchored by a frame whose camera sits on a map bound (x exact), or, on a map where none does, by the minimap dot over all frames (see Backgrounds). Cached as `<mapId>.png` (RGBA), `<mapId>.mask.png` (disagreement, 0..253; 254 too few samples; 255 unseen) and `<mapId>.json`.
- **Per frame** (`EntityDetector`). Register the frame against the mosaic (narrow search around a measured camera; otherwise a coarse search of 4x4 block means over +-64 pixels, then a fine one), difference it, classify each differing pixel as solid, a darkening (name-tag box), a whitening (steam, clouds) or bright text, open 3x3 and label components. Pixels the mosaic cannot vouch for fall back to a screen-space model while the camera rests (parallax layers hold still on screen). Name-tag boxes are found as 16-row stacks of darkened background with near-white text, fingerprinted and OCR'd once per distinct appearance, and attached to the blob standing on them. Candidates get their feet (from the tag when there is one), world position and foothold, then a nearest-neighbour tracker with a one-second memory assigns track ids, ages, velocities and kinds.
- **Kinds.** The one candidate under the pet's tag is the Pet (see The pet); a sprite match (now or earlier on the track) makes a Mob, a drop icon a Drop and a damage number read from the client's digits a Damage, decisively; otherwise a level badge, a known mob name or a name a species of the map ends with (`loar`, a Boar whose start was covered) makes a Mob; another plain name a Player; without a tag, feet on a foothold make a Mob (or a Drop when small, static and unchanging), floating short-lived blobs are Effects (spells, damage numbers too faded to read), the rest Unknown. The tracker learns mob names and levels from the tags and cleans later reads against them (`Dark Axe Stu`, `Fire BMara` with the pet's tag run into it).
- **API.** `EntityDetector.Detect(frame, width, DetectionContext)` returns an `EntityFrame` with `DetectedEntity` records: kind, confidence, screen box (the foreground blob), feet, world position, foothold id, tag text, level and name, track id, age, first frame, velocity, and for mobs a `MobIdentity` (client id, name, facing, animation, frame, score, whether matched in this frame, the capture sequence of the last match and how long it has been carried) with the `SpriteMatch` (including what its species rests on, `SpeciesBasis`), the `Hitbox` (the client's body rectangle, see Review 1) and the `State` (alive or dying), for drops the `DropMatch` (item id), for damage numbers the `DamageMatch`. The context carries the capture sequence and the EXP the status bar shows.

What fx-combat-exact (377 keyframes over 192 seconds of combat in Deep Valley I) settled about the scene:

- **Mob tags are drawn only on mobs that were hit**, together with an HP bar above them, wherever they are (on the retired fx-combat a Fire Boar hit from 300 pixels away had one), and are gone again some time later (not measured); mobs standing right next to the character but not hit have none, so they are neither always drawn nor proximity-based. So they are a strong classifier but a rare one: 7.6% of mob detections and 21.5% of mob tracks carried a readable tag. The badge reads as `Lv, 23`, `Lw, 25`, `Lv,32`, `Lw.23` or `Lv 25`; the mobs seen were Lv. 23 Dark Axe Stump, Lv. 25 Wild Boar, Lv. 32 Fire Boar, Lv. 11 Dark Stump and Axe Stump (Lv. 17 on fx-exact), Red and Blue Snails (their badges never read); also the pet Mara and one other player, KOOKAW. Pets and players have the same box without a badge.
- **Mosaic.** Built from the lossless video, anchored by frames whose camera sat on a map bound: 5,377 frames voted (156 more rejected for a poor registration), then the 349 keyframes with a measured camera replaced 17.6 M voted pixels with their own values. The vr box is 2906x2189 world units; 85.8% was seen, 84.5% often enough from shifted viewpoints, and 50.7% of that is unreliable at 25% disagreement (parallax cliffs and clouds, the waterfall, steam, mob walkways); 58.2% is usable for foreground at 45%. Registration moved the tracker's camera by up to 22 pixels on either axis and raised the median match fraction from 0.148 to 0.910.
- **Validation** (`--entity-report`, label-free): 371 of 376 keyframes on the map registered; per frame on average 5.2 mobs, 0.50 pets, 0.08 players, 0.28 drops, 2.9 effects, 1.7 unknown; 88.8% of mob detections have their feet within 6 units of a foothold (93.9% of the tagged ones); mob tracks run a median of 5 keyframes (p90 20). Of the 61 EXP gains, 95.1% have a mob track ending within 450 units from three keyframes before to one after, against 83.3% for an arbitrary frame; for hit mobs (tag or HP bar seen) 34.4% against 32.0%. Drops are few: the pet loots them within a few seconds.
- **Cost.** 12.4 ms per frame on average (median 11.6, p90 16.3; Release, keyframes, OCR and report diagnostics excluded): registration 3.3, difference 3.4, tags 1.8, components 0.8, sprites 2.8, drops 0.2, tracking 0.2; the 48 frames needing the wide registration search make the tail.
- **Limits.** Mobs in front of parallax background were only seen while the camera rested (they are now searched for along their footholds, see Review 1), and a mob idling in one spot for seconds is absorbed by the screen-space model; the mosaic knows only what the recordings showed, so a map visited briefly is mostly unreliable; tags drawn over each other OCR as one; the HP bar is seldom separable from the sprite.

### Sprite verification and identity

- **Templates per map** (`MobLibrary`, `MapMobSet`). From the map's `life` list: the distinct mob ids with their spawn counts, the floors their spawns stand on (a floor is a connected component of the foothold prev/next graph, `FootholdIndex.FloorOf`), their mobility and every frame of every animation in both facings (the stored frames face left; right is the mirror). Linked mobs share their target's frames, in-mob frame links are loaded once, and the Blue Snail's `revive` puff is left out (it matched steam). Built once per map.
- **The client draws the exported frames 1:1.** On exact captures a mob on screen is its WZ frame, pixel for pixel, at an integer position: an exhaustive search of the fx-exact and fx-anttunnel-open keyframes for every frame of every species found 59 and 27 whole mobs that agree on every visible opaque pixel (Red Snail 1026/1026, Axe Stump 3047/3047, Zombie Mushroom 2951/2951), with no colour conversion. The mob art seen so far has 4 bits per channel (every level a multiple of 17). The retired point-size recordings differed only because that capture blurred and colour-shifted the game's pixels (docs/capture-notes.md, Exactness).
- **Matching** (`SpriteMatcher`). Every fully opaque pixel of the frame (alpha 255; anti-aliased edges blend with whatever is behind) is compared with the screen pixel under it, and a placement scores the share of its visible opaque pixels that agree (at most 512 per placement, a spread subset). There is no tolerance: every whole mob the exhaustive search found agrees exactly, and the x264 video, which moves a sprite pixel by a median of 9 levels in its worst channel (p90 21, p99 38), would need 24 per channel to keep 93% of them, which is not a comparison of the game's pixels any more; hence lossy video is skipped. Pixels another sprite, a tag, a damage number or a spell covers simply disagree, so a partly hidden mob scores the share that shows, and a frame pixel whose colour equals the background behind it (the mosaic at the registered camera) is left out, since the screen shows that colour with or without the mob: on Ant Tunnel IV's black floor the black outlines of a misplaced Horny Mushroom had agreed on 41 of 512 pixels. The placement search stays integer: every offset of the +-6 x +-4 window is tried on 8 spread pixels (an exact match has a one-pixel peak a grid could step over), the 6 best on 32, and the 2 best of those are scored in full; a frame whose coarse agreement is under half the score needed is dropped there. A box may be up to half the frame's extent, because a mob that stood still through most of a short recording is partly baked into its mosaic and shows only where it has moved since. The remaining frames of the species that passed are scored too and the best wins, since a neighbouring frame of the same animation shares most pixels.
- **Colour states.** The freeze is a per-channel multiply by (255, 168, 10) / 255 in B, G, R, rounded: on fx-anttunnel-open's frozen Zombie Mushroom every art level of every channel mapped to exactly one screen level (G 85 to 56, 255 to 168; R 85 to 3, 255 to 10; B unchanged), 3161 of 3161 pixels. Steam is a light translucent layer whose alpha varies across the mob (0.04 to 0.59 over the steamed Axe Stump on fx-exact's keyframe 256, the same in all three channels to within rounding), so each pixel gets its own: a pixel agrees through steam when it is no darker than the art, one alpha between 0.03 and 0.75 explains all three channels to within 6 levels (the layer is a light grey-blue, not pure white), the art pixel is coloured (grey outlines fit any lighter grey, which spells and damage numbers supply), the screen pixel itself still shows a hue of at least one art level (17), and its right or lower neighbour fits with an alpha within 0.1. The screen-hue condition came from fx-combat-exact: seen through steam of alpha a, an art pixel keeps only (1 - a) of its chroma, and Dark Stump's die1/2 frame, a large light beige disc whose pixels barely count as coloured, fitted steam over brown rock (keyframe 342: 150 of 512 pixels, all through steam of alpha 0.64, score 0.29), two drops under a cloud (keyframe 47, 0.27) and the pet against a white wall (keyframe 102, 0.19). With it none of them reaches 0.2, matched mob detections went from 1,122 to 1,106 and the kills found as their species did not change; a floor of 12 left keyframe 342 at 0.19, and leaving out steamed pixels that the background behind them explains through the same layer brought it only to 0.25 (the mosaic is mostly unusable under the steam). Real steam stays: 280 of 1,119 accepted matches needed it for some pixels, 134 for more than a tenth, among them dying mobs fading out against light rock. The hit flash is not in the data: no candidate on the exact keyframes, the hit Lv. 17 Axe Stump and the hit, frozen Zombie Mushrooms with HP bars included, shows a uniform brightening on more than a tenth of its pixels (at most 9.3%, on spell effects), and the hit mobs matched as drawn or frozen.
- **Threshold 0.2.** Every candidate of the two short exact fixtures was scored against every species (`--entity-report`, with fx-exact's own ten-second mosaic) and joined with the exhaustive search: candidates lying on no mob reached at most 0.094 (effects 0.094, unknown blobs 0.092, the tagged candidates of the pet and the other players 0.078; on Ant Tunnel IV, with Slivan, Oakofoami, Black Kitty and Mara in view, 0.052), while candidates on a mob scored 0.57 to 1.00 on fx-exact (21) and 0.25 to 1.00 on fx-anttunnel-open (5), the two frozen ones 0.57 and 0.97, and a frozen Zombie Mushroom three quarters under a lightning bolt 0.17 to 0.25. 0.2 is twice the best non-mob. On fx-combat-exact (3,837 candidates) no candidate the tracker made a pet, a player or an effect reaches it (at most 0.19 of 1,201; those from 0.17 up are mobs the tracker took for effects, a Dark Axe Stump behind a rope and one in steam, and the pet), while 91% of the 79 tag-labelled candidates reach it for their own species (68% for another: the contest, not the threshold, settles the species).
- **Search and contest.** Each candidate's floor is the foothold under its feet or the nearest surface within 16 units. Species are tried in order: a tag read on the candidate or its track names the only ones; otherwise the species with a spawn on that floor, then jumpers by the vertical distance to their spawns, then flyers (floor-bound species never off their floors); within a group more spawns first, and the track's species first. A frame is placed with its visible extent on the box (bottoms and centres aligned; for a box at least 60 wide that fits nothing, on its left or right edge, and the rest becomes a new candidate). Frames whose extent is more than 30% smaller than the box are skipped. Without flyers on the map, candidates with no surface within 90 units below are not tried. The first frame to pass names a shape, not yet a species: recolours (Axe Stump and Dark Axe Stump, the snails) draw the same frames in their own colours, and a Dark Stump's body is a Dark Axe Stump's without the axe. So every other species is scored too. Recolours are settled among themselves on the pixels that tell them apart (`SpriteMatcher.Distinguish`): of the pixels opaque in both frames whose colours differ, the visible ones the screen explains by one frame only (as drawn or through steam) count for it, and a recolour wins with at least 8 such pixels and twice as many as the other; with fewer, the track's species is kept, else the one with more spawns. On fx-combat-exact 837 of the 1,127 mob detections matched in their frame rest on such pixels, mostly by hundreds (0 against 1,894 on a whole Axe Stump; the close ones, 714 against 429, are two stumps of either kind run into one blob), 284 on a shape no other species of the map draws, and 6 fell back. The groups then compete on the best score times the share of the blob's foreground the frame's silhouette covers, plus 0.05 for the track's species, minus 0.03 per factor e of fewer spawns.
- **Spawn counts, and the server's.** The client's `life` list caps how many mobs of a species one frame may show, but the server spawns what it spawns: fx-combat-exact shows two Axe Stumps where the list has one on 22 keyframes, each settled on hundreds of telling pixels and both whole and exact on keyframe 49 (503 of 503 and 505 of 505 pixels, with Dark Axe Stump at 0.35 and 0.39 at the same placements), and three stumps at once on the walkway where the list has one Axe Stump and one Dark Axe Stump. So a species' cap is its spawn count or, once one frame proved more, that many (`EntityDetector.CapOf`; a match proves its species when it rests on its own shape or telling pixels and scores at least 0.5). Matches beyond the cap lose their sprite (unproven ones first) and stay mobs only by what their track knew; identities carried by tracks are held to the same cap in each frame (least verified first). The report prints the proof (`Axe Stump ... spawns 1 (2 proven on frame 49)`) and flags any frame over a cap; on all fixtures there is none.
- **Identity in tracking.** A match moves the candidate's feet to the frame's origin and votes for the track's species; association adds 40 units of bonus for the same species and 60 of penalty for another (a track matched twice never takes another species); identified tracks are remembered for 5 s instead of 1.2, but past 1.2 s only a candidate matched to the same species takes them up again, so a killed mob's track cannot grab what appears next to it. `EntityTracker.Hint` gives the matcher the likely track before association.
- **The pet's tag** names the pet (the configured name, `--pet`, read alone without a badge; the own name likewise), never a mob or a drop. The geometric association gives a tag to the blob standing closest above it, which next to the pet can be a mob or a meso coin: on fx-combat-exact the pet's tag labelled 49 mob detections and 8 drops before the detector took the tag off any mob a sprite verified or drop an icon identified and gave it to another blob standing on it that nothing verified, or else to a tag alone. Since review 1 the pet is found by its tag only (see Review 1, The pet); since review 2 by its own sprite, the tag confirming it (see Review 2).
- **Drops** (`DropMatcher`). Small candidates on a surface are compared with every `iconRaw` up to 40 pixels (1022 icons with at least 100 opaque pixels, 15 of them meso coins) whose extent fits the box to 3 pixels, over +-2 x +-3, the same way as mobs (without the freeze), and need 0.8. fx-exact's one drop on the ground (item 04000004) matched at 1.00 on all four keyframes; on fx-combat-exact all 62 icon matches scored 1.00 (18 drop tracks, 11 identified: 6 as meso 09000000, 1 as meso 09000001, 4 as item 04000004), and no other of the 375 small candidates on a surface reached 0.5. A track whose icon matched stays a drop (coins spin, which the appearance test took for a mob) and continues only as the same item and a blob of about its size. When no icon fits the box, a second pass tries icons up to 8 pixels larger that hold four of the box's six commonest colours, over +-5 x +-4: a drop on background the mosaic cannot vouch for loses columns (the Leaf, 04000011, showed as a 23x21 blob of its 27x23 icon on fx-combat-exact's frames 721 and 736). Equipment icons are not exported, so equipment drops stay unidentified.
- **Tags on exact frames.** `TagDetector` OCRs a tag crop binarized, light text as black ink on white paper (`OcrInput.InkOnPaper`, as for the level badge), not softened like the status bar and the map name: on fx-exact's five crops of the pet's tag Vision read Mara on 2 as captured (lara and a cut-off Ma on the others), on none softened (empty or "BJBI") and on 3 binarized, and the mob tag as "Lw, 17", "Lw, 17" and "Lv. 17 Axe Stump"; fx-anttunnel-open's player and pet tags (Slivan, Black Kitty) read alike all three ways. ### Review 1: hitboxes, the foothold search, deaths, damage numbers and the pet

The first review of baked frames (`data/bake/fx-combat-exact/review-1/`, Arthur, 2026-10-27) found the cases below; each is now a ground-truth entry (see Ground truth) and `bake truth` checks them. Numbers are fx-combat-exact's keyframes (`--entity-report`, Release) unless noted.

- **Hitboxes.** A mob's box was the extent of its foreground blob, which over unreliable background is only the part the differencing sees (a stump's top, its lower half cut). The client's frame data has the body rectangle each frame collides with, `lt` and `rb` relative to the origin (Dark Stump move/0: lt -31,-51, rb 31,0, a 62x51 body standing on the origin); `MobLibrary` loads it into `SpriteFrame.ClientBody`, mirrored about the origin pixel for a right-facing frame as the pixels are (columns [l, r) become [1 - r, 1 - l)). An identified mob's box is now that rectangle placed with its origin on the feet: the matched frame at the sprite's origin, or for a carried identity the track's last frame at the blob's feet, put down on the foothold below within the body's height for a floor-bound species; feet within 6 units of a surface are snapped onto it. The die frames have no lt/rb (they carry `a0`/`a1`, an opacity ramp); they fall back to the frame's visible extent. 1,874 of 1,924 identified mob detections got the client's rectangle, 50 the extent. The blob stays in the stream as `blob`.
- **The foothold search** (`FootholdSearch`). Foreground differencing cannot see a mob over background the mosaic does not vouch for: over Deep Valley I's top platform 61 to 99% of the 60 rows above every foothold are parallax sky and cloud, so three Red Snails and a Dark Axe Stump standing there had no box (not a deliberate dead zone; the limit noted below for mobs in front of parallax). On an exact frame a sprite's opaque pixels equal the screen whatever is behind it, and a walking mob's feet are on its foothold, so its placement is one integer column: y follows from the line. Once per map the search marks the gaps, the stretches of footholds whose band above is at least half unusable (6,067 world columns on Deep Valley I); every frame each visible gap is searched for the species that can stand on its floor (spawned there, or jumpers). Placements come from anchors: for every frame (all poses, both facings) twelve coloured pixels on the rows 6, 14 and 22 above its feet, those the mosaic shows least, at least 4 columns apart; each screen pixel on those rows looked up by colour names a frame and a column, whose placement is probed on 8 spread opaque pixels (masked ones skipped, at most two disagreeing), and the survivors are scored in full by the strict matcher (window +-1, at least 0.4, a quarter of the pixels comparable since the own character may stand in front) and go through the species contest. The same search runs under an unmatched blob near a foothold (up to six per frame, largest first), whose box was cut by the own character's mask, an effect drawn over the mob or unreliable background. A find over an unmatched blob verifies that blob; elsewhere it is a new candidate without one. Finds standing in one place as a match already made (feet within 12 x 8 and extents overlapping half the larger) are the same mob; a snail in front of a stump is not. On fx-combat-exact's keyframes it found 383 mobs where no blob was and verified 411 blobs no box alignment matched (744 detections in the output rest on it, all species, 690 of them walking); the finds score a median 1.00, p5 0.66, minimum 0.38 after the contest, 657 of 794 at 0.9 or more. It costs 1.9 ms per frame at the mean (0.7 of it under unmatched blobs), about 11,000 placements probed and 8 fully scored.

### Temporal pass

Most of a frame is the previous frame moved on by a few pixels and a pose; spawns, deaths, attacks and effects are the surprises. So before the full search, every live identified mob track (its sprite matched within the last 1.2 s) predicts where it stands and in what pose, the strict matcher verifies the prediction, and the full search runs on what the verified predictions do not explain (`TemporalPass.cs`, a part of `EntityDetector`).

- **Pose by pose** (a track matched within the last 0.1 s, three video frames: every client frame lasts at least 70 ms, median 180, so at 30 per second no pose is skipped). The feet are the last match's moved on by the track's velocity along x, no faster than 1.5 times its walking speed, put on its foothold; the frame shown and the next one of its animation are tried there within a window of 2 pixels plus the reach of that speed (rows 2, 6 for jumpers), the next one first once the frame's delay (`delay` in data/mobinfo) has run out since the pose was first seen (by pts). When neither passes, the transitions in a fixed order: the neighbouring frames, stand and move, the other facing, hit (with 6 more columns of knock-back), die, the species' other animations. A pass scoring 0.9 or every pixel ends the search; a later group replaces an earlier group's best only when 0.02 better. A track whose kill an EXP gain credited shows only its die pose.
- **Along the foothold** (keyframes half a second apart, or a track missed for more than 0.1 s). One pose cannot be predicted, so the search is narrowed to the track's species, all its poses, its own floor and the columns its reach allows (`GateBase` 30 plus 1.5 times its walking speed over the time since its last match, plus 80 after a hit): first the stretch around where its velocity took it (half that reach), then the rest. Every placement with the feet on the line (on a slope also a row either side) is probed on the foothold search's spread pixels (exactly equal as drawn or frozen, at most two missing) and the survivors are scored strictly, nearest the predicted feet first.
- **Verification.** The existing `SpriteMatcher` with its rules unchanged (no tolerance, frozen tint, steam alpha, background-equal pixels left out), at the foothold search's bar: 0.4 of the pixels, a quarter of them comparable, since a prediction too places a frame by its origin with no blob to vouch for it. A verified prediction faces the species its pixels could also be, as any match does: recolours settled on the pixels that tell them apart, and a species drawing at least half of the frame's pixels alike (the Dark Stump's body is the Dark Axe Stump's) scored with the contest's coverage; when another species wins, the prediction does not stand and the full search decides. Two tracks predicted onto one mob (a track broken earlier and its successor): the more verified keeps it.
- **The residual.** Each verified prediction's agreeing opaque pixels and its edge (alpha below 255) leave the foreground mask, and every later comparison of the frame leaves them out like masked pixels; its disagreeing pixels stay, so something in front of the mob (the pet before a boar, a snail before a stump, a damage number) is still a blob of its own. The predicted mob joins the residual's blobs with its explained pixels' extent, so tags and HP bars attach to it as before (a tag below its frame is its own, before any residual blob's), and the foothold search skips its columns. What its frame left unexplained (steam, a fading die pose: the dying Wild Boar on frame 781 was shown twice) is dropped when nothing verified it, it is larger than a drop and its box lies half within the frame; and when the search under a piece of a predicted mob's blob finds the same mob in a better pose, the pose goes to the prediction's candidate. The full search (blobs, tags, the species search and the search under unmatched blobs, the foothold search, drops, damage numbers) runs on the rest.
- **Association.** A candidate that verified a track's own prediction continues that track before any other pair: its pixels say it is that mob, so a tag read naming another species (the screen's edge cut "Dark Axe Stump" to "Axe StumpR" on every frame of a stump at the left edge, breaking its track 30 times a second), a name read or the nearest-neighbour gate no longer break it. The death rule holds by construction.
- **Safety.** A prediction never invents anything: it is a strict match at a higher bar than a blob's, and a track whose prediction fails falls back to the carry and absence rules unchanged. Every 10th frame (and after any frame the detector did not run on) is a full frame: the full search runs on every pixel, as before the temporal pass, with the predictions verified beside it; a full-search match of the same mob and species binds to its track, one of another species is counted as drift and the prediction dropped, and a prediction the full search did not find is kept as a candidate.
- **The camera** is predicted too: the frame is first registered within 4 pixels of the previous frame's camera (a video; 89% of fx-combat-exact's frames moved 4 or fewer) or of the world tracker's camera moved by the previous registration's offset (keyframes), and accepted as a narrow search is (0.6, peak inside the window); otherwise the searches run as before.
- **Stream.** Every entity carries `found` (`prediction`, `transition`, `search`), and a matched mob's bake label ends `[p]`, `[t]` or `[s]`. `OAKSOUL_TEMPORAL=off` runs the full search alone on every frame, and `OAKSOUL_TEMPORAL_FULL_EVERY=N` sets the cadence. With the pass off, fx-combat-exact's keyframe stream is the previous build's line for line (bar the new field): the speed-ups made alongside (a frame's key computed once, the matcher's patch filled from whole pixels, the recolour count stopped once its outcome is settled) change no result.

### Foreground layers

Review 2 (frame 0000496, Arthur, 2026-10-28, as relayed: "Mob 59 blue snail and 135 boar got lost due to the cloud - from future frames it seems to struggle with this") is the white fog that drifts over the left of Deep Valley I. It is the map's `info/cloud = 1` (44 maps, all of the Perion region): the client then draws drifting clouds, the seven canvases of Map.wz `MapHelper.img/weather/cloud` (95x63 to 397x182, BGRA4444, grey 170 to 255), in front of the map's layers and its mobs (ropes in front of them). `OakSoul.MapExport` now exports `cloud` and the back layers, `OakSoul.SpriteExport --clouds` the canvases (`data/sprites/weather/cloud/<n>.png` and `cloud.json` with their origins).

- **What a cloud is** (measured on fx-combat-exact against the mosaic): one canvas, unflipped, at an integer screen position, with its own alpha G (143 to 217 among the clouds followed), at a constant world velocity, 21 to 49 units per second to the right and a fraction of a unit per second up or down. The client keeps a fixed set per visit (fx-exact, another visit of the same map, had other canvases, alphas and rows) and moves a cloud that leaves on the right back by a fixed distance: eight clouds seen before and after a wrap moved back by 3,259 to 3,266 units (two laps 6,523 and 6,524), the view range's 2,906 plus 356, with the same canvas, alpha, speed and row (the row drifting on at its own slow rate). Canvas 2 at alpha 205 left at origin x 2,260 and came back at -1,002 between two video frames: in view, since the camera stood at the left bound (none of the 4,837 background pixels its canvas then covered changed in the frame before, 5,056 of 5,315 exact in the next). Two clouds can overlap (canvas 1 at alphas 164 and 166, 30 units apart, over the snail and the boar of the review).
- **The blend**: a scene pixel p under a cloud pixel of colour c and art alpha a shows round(p + (c - p) a G / 255^2), per channel, rounded once per cloud, clouds over clouds in turn in draw order (`CloudLayer.Blend`, exact in integers: 255^2 is odd, so there is no tie). On keyframe 496, canvas 2 at alpha 205 explains 17,245 of the 18,719 background pixels it covers exactly; every other one is off by 2 levels or more and lies where the mosaic is wrong (no pixel is off by 1). Quantizing a G / 255 to 8 bits first, or rounding down, explains under 80%. Under the two overlapping clouds the Wild Boar's move/0 R frame agrees on 1,980 of 1,980 pixels, the Blue Snail's move/3 R on 1,080 of 1,084 (in the other draw order 1,100 of 1,980).
- **The mosaic without fog** (`BackgroundDefog`, a third round of `--build-background` on a map with info/cloud). Where clouds pass most (the left of Deep Valley I, where they all come back in) fogged values outvoted the background: on the wall at frames 1171 to 1261, clear in those frames, 16.2% of the mosaic was brighter than the frames. The third round follows the clouds over the replay against the first two rounds' mosaic (finding every whitened region it can, without the detector's budget, a cloud found again followed as a stretch of its own), and votes, counts and takes the keyframes' exact values again with every pixel left out that a cloud's canvas covers, widened by a column either side: where the clouds were followed at their places, before and after along their wrapped lines (780 M pixel votes left out on fx-combat-exact's video). The wall now equals the clear frames on all its pixels (83.8% before; 96.1% with the lines alone, 98.0% with one entry per cloud); 2.87 M pixels of the map are reliable, from 2.65 M. Build it with `--build-background` as before (the detector reads it from `--backgrounds`).
- **Following them** (`CloudLayer`, `EntityDetector.Clouds.cs`). Each cloud is predicted from its wrapped line and verified on 48 spread pixels of its canvas over background the mosaic vouches for (half of the pixels it changes must be exact; on video a cloud whose line rests on seconds is checked every third frame, at the predicted place first). A cloud seen five times over at least a second is part of the map's set and never dropped: out of view it is predicted on, and found again where the line puts it, the search window growing with the time since it was last seen; a discovery that finds a known canvas and alpha near its row hands the place to it, unless that cloud is laid over the frame elsewhere (the pair over the snail and the boar is one canvas at alphas 164 and 166, rows 5 apart). Overlapping clouds are placed twice, the second time with the others at their new places. Before its own line, a cloud drifts at the median of the known clouds' speeds, is searched for within the spread of their speeds (24 columns at most, a row up or down), is verified on 512 pixels spread over its canvas (a fringe at the edge of sight shows few of the 48), with pixels the screen shows whiter still left out (a second cloud not found yet over it), and stops being laid over the scene after a quarter of a second unverified.
- **Where a cloud comes into sight.** The pair that lost the snail and the boar, back-predicted from their lines: canvas 1 at alpha 164 (36.98 units per second, row 1235) and at alpha 166 (39.28, row 1240) wrapped at the wrap column 1.2 s apart (9.7 and 10.8 s), each alone, their canvases 11 and 12 columns left of the view (the camera sat at the view range's left bound), and drifted in at seq 295 and 328 over the parallax sky, where they cannot be seen; they came into sight where the left wall's background starts (screen x 40 to 60), the first alone from about seq 380, the second from about 400, and always inside the first's footprint (the first is 30 columns further right). A cloud of the visit's fixed set comes into sight across a boundary of the background the mosaic vouches for: the view's edge or unknown background beside it, by drifting (every cloud drifts right, so from the left), by a pan (toward the edge the camera moved to in the last half second) or by wrapping (its canvas's left column is then known). A whitened region on such a boundary is looked at first, among the placements that reach past that boundary with their leading edge at the region's far side (a few columns per row instead of the whole canvas); its leading fringe (32 columns) alone first when the region holds more than one cloud; a pair found together is moved a few pixels together to where both explain most. ## Overlay stream

The watcher can write everything it concluded, frame by frame, as a data stream: what the readers read, where the world model put the character and the camera, and every entity with the evidence for what it was taken to be. It is what the bake tool renders over a recording's frames for review (below), and what a live see-through window would draw later.

```
dotnet run -c Release --project src/OakSoul.Watch -- --recording recordings/fx-combat-exact --keyframes --speed 0 --overlay-out data/overlays/fx-combat-exact/overlay.jsonl.gz
dotnet run --project src/OakSoul.Watch -- --list-layers
```

`--overlay-out PATH` writes the stream (it implies `--entities`); `--list-layers` prints every layer with its item kinds and fields, and exits. The stream gets one line per frame the watcher processes: every keyframe with `--keyframes`, every frame of a video replay, every frame of a live capture.

**Format, version `oaksoul.overlay/1`.** gzip JSON Lines (`overlay.jsonl.gz`; a path not ending in `.gz` is written uncompressed). The first line is a header:

```json
{"schema":"oaksoul.overlay/1","producer":"OakSoul.Watch","commit":"<git sha, +dirty when tracked files differ>","session":"fx-combat-exact","recording":"recordings/fx-combat-exact","replay":"keyframes","source":"recordings/fx-combat-exact (keyframes)","frame":[1366,768],"name":"LynxHope","pet":"Mara","petSpecies":"5000004","petSpeciesName":"Black Kitty","thresholds":{"sprite":0.2,"drop":0.8,"coin":0.8},"layers":["world","minimap","hud","camera","tags","self","entity"]}
```

then one line per frame (fx-combat-exact's keyframe 0000391, most items left out):

```json
{"seq":391,"pts":668458.213738625,"t":13.277,"map":10004100,"camera":[-823,1055],"detect":"ok","items":[
 {"layer":"world","kind":"foothold","line":[[869,268],[1187,268]],"id":130},
```

- **Frame fields.** `seq` and `pts` are the capture's own, the join key with `frames.jsonl` and the keyframe file names (see Frame numbers); `t` is seconds into the session (pts less the first record's), `map` the map id, `camera` the camera used (world position of the screen's top-left: the registered one when the detector registered the frame, else the world tracker's). `detect` is `ok` or the detector's note (`registration failed (0.07)`) when the entity detector ran on the frame; `skip` says why it did not (`lossy video ...`, `no map`, `no background for map ...`). `filled: true` marks a video frame the recorder filled an idle gap with (below).
- **Items.** Every item has a `layer` and a `kind` (a word: mob, player, pet, drop, effect, unknown, tag, foothold, ...), then its fields. Geometry is integer pixels of the 1366x768 frame: `rect` [x, y, w, h], points [x, y] (`feet`, `point`), `line` a list of points; `label` is the text to draw. World positions are map units. Ids are the client's: mob ids 7 digits as in `data/mobinfo` (`"0000005"`), item ids 8 (`"09000000"`), map ids, foothold ids. Fields without a value are left out.
- **Evidence.** A mob carries its identity with what it rests on: `mob`, `name`, `anim`, `frame`, `facing`, `score` and `evidence`: `matched` (a sprite matched in this very frame; then also `tint` as drawn, frozen, steam or frozen+steam, `fogged` pixels, `basis` shape / pixels / track / spawns, `agree` [agreeing, compared] pixels and `sprite`, the matched frame's extent on screen), `carried` (the identity is the track's from earlier frames; the sheets' `~`; the pose is its last match's, whose score is `lastScore`, with `lastMatchedSeq` its capture sequence, `lastMatchedAt` its time and `carriedFor` the seconds since: a carried identity has no `score` of this frame) or `unverified` (a mob no sprite verified; the sheets' `?`). An identified mob's `rect` is its hitbox: `box` says whether that is the client's body rectangle (`hitbox`, lt/rb of the frame at the sprite's origin) or, for frames without one, the frame's visible extent (`sprite`); `blob` is the foreground blob it was seen as. `state` is `dying` when the die pose matched (now or last) or an EXP gain credited the kill to the track; `sweep` marks a mob the foothold search found. `found` says how the entity was found in this frame (see Temporal pass): `prediction` (its track's predicted pose verified at the predicted place), `transition` (another pose of its species verified there: a neighbouring frame, stand or move, the other facing, hit, die) or `search` (the full search; every kind but a mob and the pet is found this way); the pet also `tag` (its tag alone, its sprite not verified). When the species contest had a rival, `rival`, `rivalName` and `rivalScore` name it. `match` notes a sprite matched in the frame that the identity does not reflect (another species, or over the spawn cap). `tag` is the tag text read on it in this frame, `name` and `level` what its tags showed (for a mob with an identity, `name` is the species and `tagName` the tags' name when it differs). Drops carry `item`, `category`, `score` and `evidence`; a meso coin also its `frame` (iconRaw 0 to 3, face-on to edge-on) and `anchor` (the client's origin of its spinning frames, the same for every frame), and a drop matched in the air near a kill `inFlight`. The pet (since review 2) carries `petSpecies` (the client's pet id) and `speciesName` (Black Kitty), with `anim`, `frame`, `facing`, `score`, `agree` and `evidence` `matched` when its sprite verified it, `evidence` `tag` when its tag alone found it. An own skill effect (kind `effect`) carries `skill` (the skill id), `skillName` (Cold Beam) and the frame it matched (`anim` the skill's node, hit/0; `frame`, `facing`, `score`, `agree`). A mob with an HP bar over it carries `hpFill`, and each HP bar is an item of its own (kind `hpbar`): `rect` the bar's 52x10 frame, `fill` the current HP as a share of its 46 fill columns, `fillColumns`, `colour` (green over the red of what was lost; red over black, as on the frozen Wild Boar of frame 751; `empty`; `covered` when something hides its first column) and `track`, the mob below it. Damage numbers (kind `damage`) carry `value` (when every digit read), `digits` (`?` for an unread one between), `direction` (dealt, taken or other), `critical`, `set` (the digit family, NoRed, NoCri, NoViolet), `complete` (the first digit is a first-digit glyph), `score` (the digits' pair agreement) and `alpha` (the opacity they were drawn with). Every entity has its `track`, `age` (frames seen), `confidence`, `velocity` (units per second), `world`, `foothold` and `surface` (signed distance of the feet from the nearest surface).

| Layer | Kinds | What |
|---|---|---|
| `world` | foothold, ladder, rope, portal | the map's footholds (`wall` when vertical), ladders, ropes and portals that reach into the frame, projected through the frame's camera. A portal has its `point`, its `name`, `type`, `target` map id, `targetName` (the target portal), `destination` (the target map's name, with the street first only where another street has a map of that name), `script` when it has one, and its activation area as `rect` (none on a spawn point; streams written before have only the point); its label is the destination, "spawn" for a spawn point, else its script or name |
| `minimap` | panel, map, dot, names | the panel as read (`collapsed`), the map image, every dot (`dot` self, player, portal, npc, other), the name block with the names read (`street`, `mapName`) and the map id they resolved to |
| `hud` | region, slot, buff, cursor | the HUD layout's fixed regions labelled with their readings (`level`; `job` and `character`; `hp`, `mp` [cur, max] and `bar`; `exp` and `percent`; `slots`; `buffs`), the quickslot cells (`key`, `occupied`), the buff icons (`name`, `faded`) and the mouse cursor (`point` its hotspot, `state`, `frame`, `score`) |
| `camera` | camera | the `camera` used, the world tracker's `guess`, the registration's `offset` and `score`, the `source` that placed the character (dot+tag, dot, tag, held) |
| `tags` | tag | every name or level tag the detector found, with its OCR `text`, the `level` and `name` parsed from it (a name close to a species of the map is that species' name), and its `owner` (mob, pet, player, self or none; a tag with a level badge is a mob's) with the owner's `track` |
| `self` | tag, character | the own name tag as located (`feet`, `agree` text columns), the own character: the box the detector masked out (`masked`), the soles on screen, `world`, `foothold` or `support` (fh123, rope@86) |
| `entity` | mob, player, pet, drop, effect, damage, unknown, hpbar | each `DetectedEntity`: box (an identified mob's hitbox), blob, feet, world position, foothold, track, age, confidence, velocity, HP bar seen and its fill, identity, evidence and state as above, damage numbers' value and direction, the pet's species and pose, a meso coin's frame and anchor, an own skill effect's skill; and each mob HP bar read (`fill`, `fillColumns`, `colour`, `track` of the mob below) |

All layers are on; the registry (`OverlayLayers`) is the source of truth for kinds and fields, and `bake check` verifies a stream against it.

- **Filled video frames are emitted, flagged.** The recorder keeps the video at a constant 30 per second by repeating the last frame through idle gaps of up to two seconds (172 of fx-combat-exact's 5,775 video frames); such a frame has no capture record. Its line is written with `"filled":true`, the `seq` of the captured frame it repeats and a `pts` that frame's plus the fill's offset on the video timeline, because the watcher does process it: the trackers age, carry and drop tracks on it, so what it concluded there is part of the record and the next captured frame's state depends on it. Its pixels are the repeated frame's (the window did not change), so a consumer keyed on capture records, the bake tool's frame selection and corrections among them, simply skips filled lines; `(seq, pts)` stays unique. Frames the recorder left out of the video (`videoFrame` -1) are not in a video replay and so not in its stream; they are in a keyframe stream when they were keyframes.
- **Deterministic.** No wall-clock values or timings go into frame lines and fields are written in a fixed order, so two regenerations of a recording give identical frame lines (checked on fx-combat-exact's keyframes, and a run with `--entity-report --entity-sheet` gives the same lines as one without), and a parsed line re-serializes to the same bytes.
- **Cost.** The watcher builds each frame's `OverlayFrame` from what it already holds (`OverlayBuilder` in `src/OakSoul.Overlay`, a projection with no detection of its own) and posts it to a channel; serialization and gzip run on a writer task, as the recorder's KeyframeWriter keeps PNG encoding off the capture path. Building takes a median 0.03 ms per frame (p99 0.1 ms; on fx-combat-exact's 5,775 video frames two took over 1 ms, at most 2.3, and the first 3.2 ms while the builder is compiled; the watcher prints these at the end), and the watcher's per-frame time on that video was 17.4 and 17.6 ms writing the stream against 17.7 and 17.7 without it (Release, baseline and new run alternately), unchanged within noise. fx-combat-exact's keyframe stream is 0.4 MB (4.4 MB of JSON), its video stream 5 MB (68 MB).

## Baking frames for review

`src/OakSoul.Bake` renders the overlay stream over a recording's own frames, so what the pipeline concluded can be looked at frame by frame and pointed at unambiguously ("frame 0001411, #116 is a Wild Boar, not a Dark Stump"). It works on recordings only: nothing is captured, attached to or drawn on screen. Run it from the repository root; SESSION is a folder name under `recordings/` (or a session folder's path).

For reviewing, use the [review tool](#review-tool): the same overlay, interactive, with notes written into review packets. Baked PNGs stay for sharing a frame and for contact sheets.

```
dotnet run -c Release --project src/OakSoul.Bake -- regenerate fx-combat-exact
dotnet run -c Release --project src/OakSoul.Bake -- render fx-combat-exact --frame 1411
dotnet run -c Release --project src/OakSoul.Bake -- render fx-combat-exact --from 1:10 --seconds 15
dotnet run -c Release --project src/OakSoul.Bake -- list fx-combat-exact --frame 1411
```

- **`regenerate SESSION [--video] [--out PATH] [--character NAME] [--pet NAME|none]`** runs the current watcher pipeline (in process, `--recording SESSION --keyframes --speed 0 --overlay-out`, with `--character` and `--pet` passed on as the watcher's `--name` and `--pet`) over the recording's keyframes, or with `--video` its lossless video, and writes a fresh stream to `data/overlays/SESSION/overlay.jsonl.gz` (`overlay-video.jsonl.gz`), the watcher's log beside it (`overlay.watch.log`). It reads the background, mob and sprite caches the watcher reads (`data/backgrounds`, `data/mobinfo`, `data/sprites`, `data/maps`).
- **`render SESSION SELECTION`** writes one PNG per selected frame to `data/bake/SESSION/NAME/` (`--out DIR`; NAME from `--name` or the selection: `frame-0001411`, `frames-0000346-0000781`, `t1-10.0-15s`), named `<seq>_<m-ss.s>.png` (`0001411_0-48.0.png`: capture sequence, time into the session), plus `contact-sheet-1.png` of the selection (half-size tiles as in the entity sheets) and `items.txt` (the `list` of every frame). Frames are selected by capture sequence, the number in the keyframe file name (`--frame 1411`, `--frames 1411,1426,2000-2100` with inclusive ranges), by time into the session (`--from 1:10 --seconds 15`, seconds defaulting to 15), or `--all`; filled frames are never selected (their pixels are the frame they repeat). A frame's pixels come from its keyframe PNG when one exists for the sequence, else from the lossless video (frames.jsonl's `videoFrame`, decoded by ffmpeg with a seek half a frame early, checked equal to the keyframes on 19 spread over fx-combat-exact; `--video-pixels` forces the video). The stream is `data/overlays/SESSION/overlay.jsonl.gz` unless `--stream PATH` (or `--video`) says otherwise. `--layers a,b` draws only those layers, `--hide a,b` all but those; `--scale N` (1 to 4, default 2) magnifies the frame nearest-neighbour.
- **What a baked frame shows.** A header strip with the session, capture sequence, time, map (with the names read), camera and registration, the frame's counts (mobs matched, carried `~`, unverified `?`; other kinds; level, HP, MP, EXP) and a legend. Then the frame at 2x, with every layer drawn: footholds green, ropes and ladders brown (both 5 output pixels wide at 2x, 2.5 per game pixel, centred on the line), portals pink (each as its activation area, labelled with the name of the map it leads to; spawn points as a small square labelled spawn), the minimap's panel and dots, the HUD regions with their readings, tag boxes in their owner's colour (a mob's red, the pet's cyan, a player's blue, none grey; cyan in streams from before review 3), the own character white, and each entity's box in its kind's colour (Unknown grey, Mob red, Player blue, Pet cyan, Drop yellow, Effect purple, Damage orange, as on the contact sheets) with a cross at its feet and its label. An identified mob's box is the client's hitbox (its frame's lt/rb at the sprite's origin, the area it collides with), the legend says so, and the blob it was seen as is listed in the footer. Labels: `#116 Dark Stump move/3 R 0.97 [p]` (track, species, animation/frame, facing, score of this frame), `frozen` or `steam` when the match needed it, `vs Axe Stump 0.90` when the contest's rival came within 0.15, `dying` when the die pose matched or a kill was credited, then how the match was found: `[p]` the track's prediction, `[t]` a transition, `[s]` the full search (the footer says `found by prediction` or `found by transition`); `#28 Dark Stump ~carried 1.5 s (last move/0 R 1.00 at 23.0)` when the identity is carried by the track (the pose, score and time of its last match); `#116 Mob? Lv23 Dark Axe Stump` for a mob nothing verified, `#12 meso 09000000 1.00` or `#12 Drop?` for drops, `#173 dmg 287 dealt` or `#174 dmg 119 taken fading 0.79` for damage numbers (`?` before the digits when the first digit was not read). Labels sit above their boxes on a translucent backing, moved up past each other in a crowd with a leader line. A footer lists every entity on one line in its colour: label, rect, feet, world position, foothold, age, confidence, evidence and what it rests on, pixels agreeing, the rival, the tag read. At 2x the 5x7 font is drawn at twice its size, which reads at the image's own resolution while a label still covers no more of the game than the 1x font did on the 1x frame; `--scale 1` halves everything.
- **`list SESSION SELECTION`** prints, per frame, one line per item: layer, kind, label, rect, feet and the remaining fields (entities first). Track ids can change between regenerations, so a correction to an item is best keyed by session, capture sequence and rect (or feet), which every entity item carries in frame coordinates.
- **`sheets SESSION`** renders the watcher's `--entity-sheet` contact sheets from the stream into `data/bake/SESSION/entity-sheets/`: the same twelve frames (picked by position in the replay), tiles, colours, labels and legend. On fx-combat-exact's keyframes they are byte-identical to the sheets the watcher now writes; against the sheets written before the overlay stream existed, only the tile captions differ, which name frames by capture sequence instead of position (`frame 511` for what was `frame 35`). For a video stream the captions' times would be the capture times rather than the playback clock the watcher's sheets use.
- **`windows SESSION [--seconds S]`** ranks windows of S seconds (default 15) by what goes on in them: mob detections, plus 10 per kill (an EXP gain), 4 per drop detection and 3 per frame with the pet within 150 pixels of a mob.
- **`check SESSION [--stream PATH]`** validates a stream: every line re-serializes to the same bytes, every item conforms to the layer registry, and the frames join `frames.jsonl`: a keyframe stream holds each keyframe once in file order with the record's pts; a video stream every video frame in order, captured frames with their own sequence and pts, fills with the sequence they repeat; `(seq, pts)` unique.
- **`truth SESSION [--stream PATH] [--truth FILE]`** checks a stream against the reviewed ground truth (`truth/SESSION.jsonl`, below): one line per entry, PASS or FAIL with what is at the place, then the totals; it exits 1 when an entry fails.
- **`layers`** prints the registry, as `OakSoul.Watch --list-layers` does. **`diff A B`**, comparing two streams of one recording, is agreed but not built yet; its seam is in place (frames pair by capture sequence and pts through `OverlayStream.Captured`, and `RenderOptions.Style` restyles one stream's items over the other's).

**Review folder.** `data/bake/fx-combat-exact/review-1/` holds fifteen seconds of fx-combat-exact baked for review: its 30 keyframes from 0:11.7 to 0:26.6 (sequences 0000346 to 0000781), each at 2x with the header and the entity list, the contact sheet of all 30 and `items.txt`. `windows` ranked every 15-second window of the keyframe stream and this one came first: 231 mob detections (143 matched in their frame), 7 kills (EXP gains), 30 drop detections and the pet within 150 pixels of a mob on 5 frames, score 436; the runner-up, 1:09.9 to 1:24.7, has 221 detections (153 matched), 7 kills, 14 drop detections and the pet near mobs on 19 frames (404). `data/bake/fx-combat-exact/frame-0001411/` is a single frame baked with `--frame`. `review-1b/` is the same window baked after the first review's fixes, for comparison, and `frame-0000781/` its last frame alone.

```
dotnet run -c Release --project src/OakSoul.Bake -- regenerate fx-combat-exact
dotnet run -c Release --project src/OakSoul.Bake -- windows fx-combat-exact --seconds 15
dotnet run -c Release --project src/OakSoul.Bake -- render fx-combat-exact --from 0:11.7 --seconds 15 --name review-1
dotnet run -c Release --project src/OakSoul.Bake -- render fx-combat-exact --frame 1411
```

### Ground truth

The reviewer's statements about baked frames are kept, tracked in the repository, as `truth/<session>.jsonl`: one JSON object per line, each about one place in one frame, so every correction becomes a regression check (`bake truth`). An entry is keyed by session, capture sequence and an image position, never by track id, which changes between regenerations:

```json
{"id":"r1-781-boar","session":"fx-combat-exact","seq":781,"rect":[774,462,48,34],"expect":{"kind":"mob","nameEndsWith":"Boar","state":"dying"},"note":"Review 1, frame 0000781 (as relayed): '#28 Dark Stump move/0 R 1.00~' is a dying boar.","source":"Arthur, review 1, 2026-10-27"}
```

- **Place.** `rect` [x, y, w, h] in frame pixels (the box the reviewer pointed at), or `point` [x, y] for something the pipeline missed; `near` (pixels) grows it. An entity is at the place when its rect contains the point (a pixel of slack), or for a rect when the two overlap by 30% of the smaller or either contains the other's centre; with `near`, when its rect meets the grown place.
- **`expect`**: `kind` (some entity of that kind is there, and satisfies every other condition given: `nameEndsWith`, `nameContains`, `name` exactly, `state`, `direction`, `covers` points its rect must contain, `excludes` points it must not, `fields` values it must have (`{"skillName":"Cold Beam"}`, `{"category":"meso"}`), `fieldsNot` values it must not have (`{"state":"dying"}`), `range` numeric fields within [min, max] (`{"fill":[0.5,0.65]}`); `count` exactly this many such entities at the place, one mob one track, and `minCount` at least this many); `notKind` (no entity of these kinds there); `none` (no entity at all there); `self` (the own character's box covers the place's centre); `hudKind` (a HUD item of that kind at the place, the cursor); since review 3 `layer`, the layer the other conditions look at instead of the entity layer (`{"layer":"tags","kind":"tag","fields":{"owner":"mob"}}`, a tag whose owner is a mob).
- **Streams.** An entry about a frame a stream cannot hold reports `n/a` for that stream rather than failing: a video-only sequence (between keyframes) against the keyframe stream. A frame the stream should hold but does not still fails.
- **Provenance.** `note` holds the reviewer's words (or the coordinator's relay of them, marked so), `source` who said it and when, `basis` anything the entry's author added to make it checkable (a point placed on the body the reviewer named, the reviewed label), so an entry states only what the reviewer said. Species are recorded only when the reviewer named them.

`truth/fx-combat-exact.jsonl` holds review 1's thirteen entries: the three snails and the stump on the top platform of frame 0000781 are mobs (points), the stump at 222,667 is a stump whose box covers its body down to its feet, the object at 774,462 is a dying boar, 734,392 holds two damage numbers (orange dealt, purple taken); on frame 0000751 the 33x21 object at 861,471 is a dropped item (the leaf and branch), the pet Mara is the cat at 756,450, the 16x38 object at 698,430 is part of LynxHope, not the pet, the 20x66 object at 825,319 is the Ice skill's shard, not a Wild Boar, and the Wild Boar's box covers the boar alone, not the pet beside it. The stream generated at the review (commit f4f829c) fails all thirteen; the current pipeline passes all thirteen. Review 2's twenty-four entries (ids `r2-`) follow: the pet at 436, 661, 746 and 748, the pet's tag fragments that are no player (571, 760), the coins (496 under the ladder, 541 and 748 edge-on), the HP bars (751 read at 0.5 to 0.65, 755 not a mob), the frozen boar counted once on 755 with its badge piece no mob, and not dying on 748, the cliff on 748, the spawning Dark Stump on 451, the snail inside the log on 751, the cursor on 346, the two Cold Beam shards on 346, the ladder stump counted once on 737 and 757, the top platform's Dark Axe Stump on 781, and the stump on the slope at the top of keyframe 2161. ## Review tool

`src/OakSoul.Review` is a desktop window (Avalonia 11, dark Fluent theme) for reviewing a recording frame by frame: the overlay stream drawn over the frame as vectors (Bake's colours and labels, sharp at any zoom), what a baked frame's header and footer say as panels, every track over time, the ground truth checked against the stream, and review notes written straight into packets. Recordings only: it never captures the screen or touches the client. Run it from the repository root (or pass `--root DIR`):

```
dotnet run -c Release --project src/OakSoul.Review -- fx-combat-exact
dotnet run -c Release --project src/OakSoul.Review -- fx-combat-exact --video --frame 781
```

Without a session it opens on the list of recordings, in keyframe or video mode. The stream is `data/overlays/SESSION/overlay.jsonl.gz` (`overlay-video.jsonl.gz`). When it is missing, the window regenerates it in the background: a child process runs Bake's `regenerate` into `overlay.jsonl`, the window reads that file as it grows, and gzips it into place when the watcher finishes. Frames can be browsed as far as it has got; the rest is greyed. A stream whose header does not match the checkout (commit, replay mode, thresholds, layers, and `--character`/`--pet` when given) is marked stale, or "uncommitted code" when the stream or the checkout has uncommitted changes (a commit cannot name such code, so the tool cannot tell whether they match), next to a Regenerate button. Only files that can change a stream count: the review tool, its tests, the documentation, `reviews/` and `truth/` are left out of both the commit comparison and "+dirty" (`OverlayProvenance.Unaffecting`), so editing the tool does not age its streams. Labels (the overlay's, the notes' and the truth entries') are part of the frame's picture: laid out in game pixels at Bake's size and drawn through the same zoom and pan as the pixels, so the view zoomed and panned anywhere shows what an exported frame would, and moving the view never moves a label. Overlapping labels stack in one fixed order (the HUD's and the map's first, then entities by track, oldest nearest its box), and a raised label keeps its place until the space below has been free for a quarter second, so labels hold still in playback. Fields the tool does not know (a newer pipeline's) are read and shown, flagged as new. `--reviewer NAME` (default Arthur) names the reviewer in packets and promoted truth.

- **Review tab.** The frame nearest-neighbour at any zoom (zoom 2 on a Retina display is the game's own size; the wheel zooms smoothly and snaps to whole zooms, Fit fills the view); drag or Shift+wheel to pan; until you zoom or pan, the frame refits when the view changes size. A bar over the frame shows which frame is on screen ("Frame 53 / 377" and its time) and the legend: a chip per entity kind in its colour, per layer, and for labels, notes and truth entries; clicking a chip switches it on or off (off is dimmed). The side panels start collapsed and open with [ and ] (or the Info and Inspector buttons). The left one holds the frame (sequence, time, camera), HUD and entity-count panels, each a fixed number of lines. Hover an entity for its details; click it to select its track: the inspector, in the right panel, shows its full record and a strip of its history (green matched, amber carried, red unverified), and clicking a cell goes to that frame.
- **Tracks tab.** One row per track across the recording, coloured by evidence, map changes as blue lines, dying frames as dots, a white bar where a track ends, so fragmentation shows at a glance. Filter by kind and length; order by first seen, name or length; click a row to open that frame with the track selected.
- **Events tab.** Every frame where something happened, in order, and under it what: kills (EXP gains), map changes, review notes and truth entries (PASS or FAIL). Click a frame or an event to go there (a note or entry also centres its region).
- **Notes tab.** The notes of the session's packets grouped by frame, each with its two crops (raw, and with the overlay as shown), and every entry of `truth/SESSION.jsonl`, PASS or FAIL against the open stream (Bake's truth check; a note is checked when it says what is really there). Click one to go to its frame and region.
- **Timeline.** Map changes (blue), notes (yellow) and failing truth entries (red); click or drag to scrub.

The transport: start, back a frame, play or pause, forward a frame, end, the speed asked for, and the speed playback actually runs at (lower when decoding falls behind). Keys: ← → a frame (pausing), with Shift 5 seconds; Home and End the start and end; Space play or pause, S cycles 0.25x, 1x and 2x; Cmd+G goes to a frame by its number (1 is the first); N note (drag a rectangle or click a point, then type), Esc cancels it; +, − and 0 zoom and fit; L labels; O open; [ and ] the left and right panels; Cmd+1 to 4 the tabs. The note editor opens the right panel with a preview of the captured area (the crop the note keeps, with the overlay), the frame, sequence, time and the region's game pixels, and the words focused: Shift+Enter saves and gives the focus back to the frame, Esc cancels.

**Review packets.** Press N and drag a rectangle (or click a point), type the note and press Shift+Enter. The editor asks nothing else: its notes have category `other` and no expectation. Notes written with a category and an expectation (earlier packets, or written to a packet by hand) keep them, and only those can be promoted to truth. The note is appended at once to `reviews/SESSION/YYYY-MM-DD-N.jsonl` (gitignored, like the recordings and crops its notes point at; what a note establishes is kept in git as its truth entry, with the words verbatim): today's latest packet, or a new one, which is the next review round ("New packet" starts one). One JSON object per line: `id`, `packet`, `review`, `reviewer`, `created`, `session`, `mode`, `seq`, `pts`, `t`, `rect` or `point`, `category`, `expect` (`kind`, `name`, `state`, `notKind`), `note` (the words verbatim), `entities` (the stream's entities at the region: id, kind, label, rect, score, evidence), `stream` (its path and header provenance), the visible `layers` and `kinds`, and `crops`: the region plus 24 pixels at 4x, raw and with the overlay as shown, in `data/reviews/SESSION/PACKET/NNN-raw.png` and `NNN-overlay.png` (gitignored). **Promote to truth** turns notes that say what is there into entries of `truth/SESSION.jsonl` in the format above: a kind with `nameEndsWith` and `state`, "nothing" as `none`, a kind it is not as `notKind`, and for a wrong box `covers` at the drawn rect's inner corners; id `r<review>-<seq>-<what>`, the words in `note`, source "Arthur, review N, date". The entries are shown before they are appended, and each note records its entry's id.

`dotnet test src/OakSoul.Review.Tests` renders the window headless over fx-combat-exact (and regenerates fx-exact's stream into a scratch folder), writing screenshots to `data/review-shots/`; without the recordings those tests check nothing.
